## 1. 六爻排盘引擎

### `iching-shifa`（npm，v1.8.0）

- **能力**：本卦 / 之卦 / 互卦 / 六亲 / 六兽 / 世应 / 伏神 / 旁伏神 / 神煞 / 纳音 / 旬空 / 节气；六种起卦法
- **许可**：**GPL-3.0-or-later** ⚠️
- **依赖**：`tyme4ts`（同作者的历法库）
- **结论**：能力确实完整，但 **GPL 有传染性**——引入到分发的产品里，整个产品需以 GPL 开源。自用无所谓，商用要慎重。

### 用它的地方：当"裁判"，不当"零件"

我拿它和我们的引擎做了**全量三方对比**：

```
共比对 64 卦 × 6 爻 = 384 爻
我方 vs iching-shifa 不一致：0
```

**384 爻零差异**。这比任何"我觉得对"都有说服力——说明手写引擎（八宫、纳甲、六亲）经得起独立实现检验。

同类还有 `@taoracle/najia`、`@astralium/liuyao`、`iching-liuyao`，未逐一验证。

> **建议**：不替换引擎（已验证正确，且没有许可负担），把 `iching-shifa` 留在 `.verify/` 作为**回归测试基准**，不进生产依赖。

## 2. 64 卦结构数据（含坑）

### `orikami048/bazi-liuyao-database`

- **内容**：`data/liuyao/64_hexagrams.json`（103KB），每卦含 宫/五行/卦型/世应位/六爻纳甲/六亲
- **许可**：**PolyForm Noncommercial 1.0.0**（仅限非商业）
- **质量**：⚠️ **有系统性错误**

交叉核对结果：

```
第三方 JSON vs 我方 不一致：32 处
样本：地山谦 2爻 我方官鬼 / 第三方JSON 妻财
      雷山小过 2爻 我方官鬼 / 第三方JSON 子孙
```

**错误规律**：全部集中在「艮」卦的纳甲——该数据集把艮的内卦排成「丙辰、丙寅、丙子」（逆行），而正确是「丙辰、丙午、丙申」（阳卦顺行）。艮作上卦或下卦共涉及 16 卦，每卦错 2 爻 = 32 处。

**这个坑很值得记**：这份数据看起来非常规范（字段齐全、命名专业、有 README 有 CLI），肉眼完全看不出问题。**结构化 ≠ 正确**。

> **建议**：可作为测试数据，**不可作为生产数据**。这也反过来证明我们保留自研引擎是对的。

## 3. 卦辞爻辞（真正能直接用的部分）

### `poplolioi11/yigua-wuyingdian-lines` ⭐ 推荐

- **底本**：康熙五十四年（1715）武英殿刊《御纂周易折中》
- **内容**：64 卦 × 6 爻 = **384 条爻辞**，含爻题（初九、九二…），附逐爻影像来源
- **许可**：**古籍原文属公有领域，明确允许使用、重制、商用**，仅"请求"保留署名（非强制条件）
- **完整性**：已验证 64 卦、每卦 6 爻、共 384 条

样本（乾卦）：
```
初九：潛龍勿用
九二：見龍在田利見大人
九三：君子終日乾乾夕惕若厲无咎
九四：或躍在淵无咎
九五：飛龍在天利見大人
上九：亢龍有悔
```

**两个注意点**：
1. **繁体**——原文是繁体，站内若要简体需转换（或用繁体呈现，古籍本来也常以繁体示人）
2. **缺卦辞**——scope 明确写「不含卦辭」，只有爻辞

### 卦辞的补充来源

- **维基文库 周易**（zh.wikisource.org）：全文 + 十翼（彖上下、大象、小象、文言、系辞上下、说卦、序卦、杂卦），CC BY-SA 4.0，可通过 MediaWiki API 直接取
- **ctext.org**：有全文，但 Cloudflare 人机验证，**无法程序化抓取**

> **建议**：爻辞用武英殿本（PD、可商用、有溯源），卦辞从维基文库补（64 条，量小）。

## 6. 结论与建议

### 立即可做（成本低、收益明确）

1. **接入 384 条爻辞**（约 1 小时）
   - 需要：卦序映射（数据集用 1–64 文王序，我们用上下卦命名）+ 繁简决策
   - 价值：卦盘每爻可展开看爻辞，站点从"工具"变成"有出处"的研习站
2. **把 `iching-shifa` 固化为回归测试**（约 0.5 小时）
   - 每次改引擎跑一遍 384 爻对比，防止手滑

### 不建议做

- ❌ 引入 `iching-shifa` 到生产依赖（GPL-3.0 传染）
- ❌ 用那份 64 卦 JSON 做生产数据（艮卦纳甲错误）
- ❌ 抓 ctext.org（Cloudflare 防护，且条款不清）

### 必须自己做

- ✅ 《增删卜易》22 章原文校对
- ✅ 案例整理（从视频里）

## 7. 一条经验

这次调研最值钱的不是"找到了什么"，而是**发现了一份看起来很专业的数据是错的**。

那份 64 卦 JSON：字段命名规范、有 README、有 CLI、有 SQLite、有在线 Demo——**所有信号都指向"可信"**。但它的艮卦纳甲是错的，而且错得很隐蔽（只影响 16 卦中的 2 爻，不逐爻核对根本发现不了）。

所以对第三方内容数据，判断标准不是"看起来专不专业"，而是：
1. **有没有明确的底本/出处**
2. **许可是否写清楚**
3. **能不能和独立实现交叉验证**

武英殿本那份爻辞三条都满足（有底本、有影像溯源、公有领域声明清晰），这才是能直接用的。
